01 · Overview

Overview & principles

Pick a place by tapping a world map, searching, or typing coordinates. The app fetches real elevation, imagery, map features and climate for that point, builds a 3D world in true metres around it, and drops you in the middle with a drag-to-look 360° camera.

Hard constraints

  • No self-hosted server. The device talks directly to free public sources; no proxy, account or backend.
  • Free, no paywall. No purchases, subscriptions or locked tiers; no paid API keys.
  • Mobile-first. Smooth on a mid-range phone; desktop may be prettier, mobile budgets win.
  • Few-minute loading. Progress is real per-stage work, never a fake timer.

Design invariants

  • One unit is one metre — horizontally and vertically, end to end.
  • Real data first. Procedural rules run only on absence of real data for a layer, never on top of it.
  • Data contracts before visuals. Generation never parses provider JSON or PNG; fetchers normalise into LocationData.
  • Attribution is UI. Credits shown in-app come from the fetchers actually used.
Figure 1. Layered architecture. Every layer lives in one Godot project; the only network traffic goes straight from the device to the public sources listed in the data-source register.

The stack is deliberately small: Godot owns UI, networking and rendering (no Flutter, no web view); GDScript is the only runtime language; Blender and GDAL are developer-machine tools whose output is committed to assets/. Godot's renderer targets Vulkan/Metal-class devices with Compatibility as the fallback.

02 · Screens

Screens & user flow

scripts/main.gd is the screen manager. It owns the pipeline, the cache store and the settings, wires their signals to the screens, and shows exactly one screen at a time.

Figure 2. Screen state machine. A generation id is bumped on every start and cancel, so a world still building on its thread is dropped once superseded; starts are ignored while a run is in flight.

Interaction model

  • Map picker — a Godot-native map of real OSM raster tiles (MapTileView), centred on the selection; a progressive preview loads first, then detail centre-out.
  • Search — Nominatim, user-triggered only (no autocomplete), one request in flight, plus a bundled gazetteer and raw coordinates.
  • Loading — five stage rows driven by stage_changed and progress_changed; cancel returns to the picker within a second.
  • 360 view — drag to look (yaw wraps, pitch clamps), pinch/scroll zoom, time-of-day slider with a "now" button, season and weather conditions, compass and attribution.
  • Responsive — one 390×844 pt design frame, canvas_items stretch, and phone / tablet / desktop breakpoints in responsive.gd.
Phone frame: picker, loading, 360 view.

04 · Pipeline

Generation pipeline

GenerationPipeline (scripts/generation/pipeline.gd) runs five frozen stages. All network fetches start together in run() and overlap; each stage awaits only what it needs, with a bounded wait so a slow source degrades a layer instead of blocking the view.

Figure 4. Overlapped fetch timeline (schematic). Stage rows are emitted as stage_changed(i, label, "in_progress" | "done"); progress_changed reports real items done/total, never a timer.

Fallback chains

Fallbacks run only on absence of real data, in a fixed order per layer. They log with print (an expected outcome offline), so a permanently broken endpoint is found by grepping for fetch failed.

After stage 3 the pipeline constructs GroundTruth once and View360 builds the world on a background thread. A cancel bumps the generation id in main.gd, so a superseded world is freed rather than shown.

05 · World model

World model

The world-model contract (docs/world-model-contract.md) freezes three things: the LocationData fields, the pipeline stage order, and preset semantics. Changing any of them needs a contract task first.

Figure 5. Data contract. Builders take (data: LocationData, ground: GroundTruth), emit metre-space Node3D subtrees, and build materials only through MaterialLibrary.

Units and the render origin

WorldScale owns every conversion. One unit is one metre horizontally and vertically — the v1 220-unit world and adaptive vertical squash are gone. +X is east, +Z is south (north is −Z).

The detailed world is 2400 m across (DETAILED_EXTENT_M). The render origin is set once per place at the viewpoint (lat, lon, centre_elevation_m), so the camera always works near the floating-point sweet spot.

GroundTruth

Built once per place from DEM posts, OSM polygons and waterways: a smoothed surface flattened only where OSM says so (building pads, roads) with water carved in. All samplers are pure bilinear reads — outside the extent they clamp to the nearest edge and never return NaN.

06 · Assembly

World assembly

TerrainBuilder.build_world(data, ground) assembles the scene in dependency order. Later layers sample the surfaces earlier ones define, so trees never land on roads, buildings or water.

Figure 6. Build order. Each builder returns a contract subtree; _adopt_flat lifts its children into the root and records the layer they came from.

Building subsystem

Buildings are the largest subsystem (≈20 classes). Real OSM footprints are extruded first; procedural infill is absence-only and style-matched (InfillPlanner, SettlementMap) and never contradicts mapped data.

Terrain, water, roads

  • Terrain — 96–256 mesh posts per side by preset over the 256-post GroundTruth; satellite drape and land-class tint in GroundMaterial's shader.
  • Water — triangulated OSM water, width-aware waterways, coastlines, shore aprons and stone quays where OSM implies built waterfront.
  • Roads — attributed OSM roads as draped ribbon meshes; street furniture and barriers from StreetProps.

Vegetation & climate

  • ClimateModel is the sole interpreter of CHELSA normals: snow line per season, treeline, biome and summer dryness.
  • TreeSpecies picks a species mix from climate and land cover; TreeMeshLibrary builds procedural meshes, instanced near and impostors far.
  • VegetationMask rasters keep trees and props off roads, buildings and water.

07 · Rendering

LOD & rendering

The 360 camera never translates, so level of detail is static: LodRing writes Godot visibility ranges once per build, with a 12% fade hysteresis. A preset switch only re-runs apply() — nothing is rebuilt, moved or recoloured.

RingReachContent

Reach ranges span Fast → Ultra (DETAIL_M, TREES_M, FAR_CITY_M in lod_ring.gd). Draw calls scale with cells × materials, not with buildings.

Atmosphere, sun and weather

The view opens on the place's golden hour; the time slider and "now" button move the true solar position for the location's date. Live Open-Meteo weather drives cloud cover and precipitation, and RoofSnow and ClimateModel lay snow on roofs and ground from the season and CHELSA snow days. RenderQuality adds the photoreal layer per tier (SSAO, volumetrics, window recesses on Ultra).

09 · Cache

Caching & offline

Two independent caches with separate budgets: the data cache holds fetched tiles and responses, the world cache holds finished worlds. A ~200 MB world can never evict the DEM, OSM or satellite tiles it was built from.

Figure 9. Revisit path. Headless test runs (dummy renderer) bypass the world cache entirely.

History

CacheStore is also the history store: a JSON file in user://. Generated terrain is reproducible from the stored coordinates and seed, so history entries double as cache keys and carry their v2 key set.

Versioning

Legacy v1 keys (dem_, sat_, osm3_) are ignored, never migrated; the LRU reaps them first under cap pressure. Area keys quantise coordinates to round(deg × 1000).

Offline download

"Download for offline" in the picker runs OfflineDownloader, which warms every on-device cache for a place — DEM, imagery, OSM, far field and climate — with progress in the picker and a history entry on success.

Offline gate: with networking disabled, a cached place loads in seconds and renders identically. An uncached place offline still renders, falling back to the deterministic procedural DEM.

10 · Landmarks

Landmarks

Recognisable structures come from two paths. A curated registry of famous landmarks is modelled on the fly in true metres; any other notable OSM feature near the viewpoint is matched to an archetype (church, tower, dome, stadium…).

How a landmark is made

  • LandmarkMesh accumulates merged geometry; LandmarkMaterials supplies calibrated photographic PBR materials.
  • Models are generated on device — no downloads. assets/eiffel.glb is the Blender pipeline proof (assets_src/blender/).
  • Up to five nearest OSM candidates per view become LandmarkArchetypes, within the haze limit.
  • The registry landmark stays the hero; the spawn view frames it from a readable distance.

11 · Code

Code organisation & testing

Every class is one GDScript file under scripts/ and stays at or under 500 lines; tools/check_class_size.sh fails the build on any violation. Large concerns split into focused helpers (for example building_builder → walls, heights, detail, roofs).

Package responsibilities

data/Fetchers, parsers, contract, cache, history
generation/Pipeline, ground surface, every builder, materials
render/Camera, atmosphere, LOD, governor, presets, world cache
screens/Picker, map tiles, loading, 360 view, history, settings
scripts/*.gdScreen manager, theme, HUD style, responsive rules

Conventions

  • Each class opens with a ## doc comment stating its responsibility and the contract or plan task it implements.
  • Static builders with (data, ground) signatures; heavy mesh work on a background thread via MeshArrays.
