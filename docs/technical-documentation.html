01 · Overview

Overview & principles

Pick a place by tapping a world map, searching, or typing coordinates. The app fetches real elevation, imagery, map features and climate for that point, builds a 3D world in true metres around it, and drops you in the middle with a drag-to-look 360° camera.

Hard constraints

  • No self-hosted server. The device talks directly to free public sources; no proxy, account or backend.
  • Free, no paywall. No purchases, subscriptions or locked tiers; no paid API keys.
  • Mobile-first. Smooth on a mid-range phone; desktop may be prettier, mobile budgets win.
  • Few-minute loading. Progress is real per-stage work, never a fake timer.

Design invariants

  • One unit is one metre — horizontally and vertically, end to end.
  • Real data first. Procedural rules run only on absence of real data for a layer, never on top of it.
  • Data contracts before visuals. Generation never parses provider JSON or PNG; fetchers normalise into LocationData.
  • Attribution is UI. Credits shown in-app come from the fetchers actually used.
Figure 1. Layered architecture. Every layer lives in one Godot project; the only network traffic goes straight from the device to the public sources listed in the data-source register.

The stack is deliberately small: Godot owns UI, networking and rendering (no Flutter, no web view); GDScript owns the app, with optional C++ GDExtension kernels for geometry and ground processing; Blender and GDAL are developer-machine tools whose output is committed to assets/. Godot's renderer targets Vulkan/Metal-class devices with Compatibility as the fallback.

02 · Screens

Screens & user flow

scripts/main.gd is the screen manager. It owns the pipeline, the cache store and the settings, wires their signals to the screens, and shows exactly one screen at a time.

Figure 2. Screen state machine. A generation id is bumped on every start and cancel, so a world still building on its thread is dropped once superseded; starts are ignored while a run is in flight. A place that takes longer than 10 minutes is stopped and returns to the map with a plain message. Esc steps back one screen.

Interaction model

  • Map home — a turning globe, then OpenFreeMap vector tiles drawn in the design system's Map style with Terrarium hillshade (scripts/map/); landmark markers from the registry and Wikipedia; OSM raster tiles as the fallback.
  • Search — instant on-device predictions, then debounced Nominatim results with one request in flight; raw coordinates and pasted view links work too.
  • Loading — four stage rows plus "Building the scene", driven by stage_changed, stage_progress and the build's phases; the terrain lens previews data as it lands; cancel returns within a second.
  • 360 view — drag to look, pinch/scroll zoom, sun-arc time and date, seasons, live weather, compass and callouts; tools: walk, time-lapse, horizon labels, mini-map, photo, view links, nearby landmarks.
  • Responsive — one 390×844 pt design frame, canvas_items stretch, and phone / tablet / desktop breakpoints in responsive.gd.
Phone frame: map home, loading, 360 view (captured November 2026).

04 · Pipeline

Generation pipeline

GenerationPipeline (scripts/generation/pipeline.gd) runs four named loading stages. Optional land-cover and canopy rasters join the imagery stage; the stage order stays fixed. All network fetches start together in run() and overlap; each stage awaits only what it needs, with a bounded wait so a slow source degrades a layer instead of blocking the view.

Figure 4. Overlapped fetch timeline (schematic). Stage rows are emitted as stage_changed(i, label, "in_progress" | "done"); stage_progress and progress_changed report real items done/total, never a timer. GroundTruth starts on a worker thread as soon as the OSM data is in, so it overlaps the far-city and climate waits. LandcoverFetcher starts with the other requests on Balanced and above; a 45 s deadline from fetch start bounds its wait.

Fallback chains

Fallbacks run only on absence of real data, in a fixed order per layer. They log with print (an expected outcome offline), so a permanently broken endpoint is found by grepping for fetch failed.

A cached payload is served before any of this; missing tags fall back to documented defaults inside the parser. After the last stage the pipeline waits for BuildPrewarm, then View360 builds the world on a background thread through WorldBuildGraph ("Building the scene"). A cancel or the 10-minute timeout bumps the generation id in main.gd and asks a running build to stop at its next stage (BuildAbort), so a superseded world is freed rather than shown and never cached.

05 · World model

World model

The world-model contract (docs/world-model-contract.md) freezes three things: the LocationData fields, the pipeline stage order, and preset semantics. Changing any of them needs a contract task first.

Figure 5. Data contract. Builders take (data: LocationData, ground: GroundTruth), emit metre-space Node3D subtrees, and build materials only through MaterialLibrary.

Units and the render origin

WorldScale owns every conversion. One unit is one metre horizontally and vertically — the v1 220-unit world and adaptive vertical squash are gone. +X is east, +Z is south (north is −Z).

The detailed world is 2400 m across (DETAILED_EXTENT_M). The render origin is set once per place at the viewpoint (lat, lon, centre_elevation_m), so the camera always works near the floating-point sweet spot.

GroundTruth

Built once per place from DEM posts, OSM polygons and waterways, on a worker thread as soon as the OSM data is in: a smoothed surface flattened only where OSM says so (building pads, roads) with water carved in. GroundIndex and PolygonIndex grids answer land-class, building and point-in-polygon lookups exactly like the full scans they replace. All samplers are pure bilinear reads — outside the extent they clamp to the nearest edge and never return NaN.

06 · Assembly

World assembly

WorldBuildGraph runs seven builder tasks on WorkerThreadPool, then adopts their subtrees in a fixed order matching the serial build. Every layer reads LocationData and the same GroundTruth; vegetation masks keep trees off roads, buildings and water.

Figure 6. Adoption order. Each builder returns a detached contract subtree; _adopt_flat lifts its children into the root and records the layer they came from. A stop request (BuildAbort) returns an empty world; if the shared PBR material cache overflows, the build reruns serially for an exact order.

Building subsystem

Buildings use regional styles, street-wall composition and footprint detail. Real OSM footprints are extruded first; procedural infill is absence-only and style-matched (InfillPlanner, SettlementMap) and never contradicts mapped data.

Terrain, water, roads

  • Terrain — 96–256 posts per side over GroundTruth; class-based PBR and imagery tint. WorldCover fills unmapped ground classes.
  • Water — coastal classification, stitched shorelines, rivers and mapped quay edges; inferred banks retain provenance. Piers and marinas follow mapped geometry.
  • Roads — draped OSM ribbons, sidewalks, rail and tram beds; mapped parking, street furniture, barriers and vehicles dress the streets.

Vegetation & climate

  • ClimateModel is the sole interpreter of CHELSA normals: snow line per season, treeline, biome and summer dryness.
  • TreeSpecies picks climate-based species; CanopyVegetation adds trees from canopy heights, then WorldCover tree cover, preserving mapped trees and masks.
  • VegetationMask rasters keep trees and props off roads, buildings and water.

07 · Rendering

LOD & rendering

The 360 camera never translates, so level of detail is static: LodRing writes Godot visibility ranges once per build, with a 12% fade hysteresis. A preset switch only re-runs apply() — nothing is rebuilt, moved or recoloured.

Reach ranges span Fast → Ultra (DETAIL_M, TREES_M, FAR_CITY_M in lod_ring.gd). Draw calls scale with cells × materials, not with buildings.

Atmosphere, sun and weather

Curated presets can choose a daylight opening; other views use the place's golden hour; the sun arc and date picker move the true solar position for the location and any calendar date, and the time-lapse plays the day. Live Open-Meteo weather drives cloud cover and precipitation through WeatherLook, with LightningRig strikes only in thunderstorms; CityLights lights windows at dusk. RoofSnow and ClimateModel lay snow on roofs and ground from the season and CHELSA snow days. RenderQuality adds the photoreal layer per tier (SSAO, volumetrics, window recesses on Ultra).

09 · Cache

Caching & offline

Two independent caches with separate budgets: the data cache holds fetched tiles and responses, the world cache holds finished worlds. A ~200 MB world can never evict the DEM, OSM or satellite tiles it was built from.

Figure 9. Revisit path. Headless test runs (dummy renderer) bypass the world cache entirely.

History

CacheStore is also the history store: a JSON file in user://. Generated terrain is reproducible from the stored coordinates and seed, so history entries double as cache keys and carry their v2 key set. Each entry also keeps the camera as you left it (ViewLink) and a picture of the view (PlaceThumb, user://thumbs). The preset shelf uses bundled daytime JPEGs from assets/preset_thumbs/; personal history snapshots stay separate.

On macOS user:// is ~/Library/Application Support/Planet Render 360; UserDirMigration moves data from Godot's default directory on the first launch after the switch.

Versioning

Legacy v1 keys (dem_, sat_, osm3_) are ignored, never migrated; the LRU reaps them first under cap pressure. Area keys quantise coordinates to round(deg × 1000).

Offline download

"Download for offline" in the picker runs OfflineDownloader, which warms every on-device cache for a place — DEM, imagery, OSM, far field and climate — with progress in the picker and a history entry on success.

Offline gate: with networking disabled, a cached place loads in seconds and renders identically. An uncached place offline still renders, falling back to the deterministic procedural DEM.

10 · Landmarks

Landmarks

The registry now has 504 bespoke landmarks: 23 core entries, 480 entries in 34 regional batches, and Riddarholmen in a shared core builder. Models are built on device in true metres. Other OSM landmarks keep their mapped building parts or use an archetype. Wikipedia supplies markers and details.

Figure 10. All 504 wired registry sites, plotted from their source coordinates; dense city sites overlap. Regional batches share geometry kits and materials. Trigger radii are entry-specific; the model retains its true bearing and distance.

How a landmark is made

  • LandmarkMesh merges geometry, LandmarkMaterials supplies calibrated PBR; models are built on device (assets/eiffel.glb proves the Blender path).
  • LandmarkSites: 10 / 16 / 22 / 26 extra candidates beside the primary (Fast → Ultra). Registry extras cap at 6 / 12 / 18 / 22; dense Ultra skylines can use 26.
  • LandmarkFidelity keeps a well-mapped landmark's real building and its building:part domes; the rest become LandmarkArchetypes.
  • WikiFetcher markers and the LandmarkCard on the map and in the view; LandmarkVisit picks the standoff for Go there.

11 · Code

Code organisation & testing

Every class is one GDScript file under scripts/ and stays at or under 1000 lines; tools/check_class_size.sh fails the build on any violation. Large concerns split into focused helpers (for example building_builder → walls, heights, detail, roofs; view_360 → chrome, conditions, tools, walk).

Source snapshot e0ec261, audited 4 November 2026: 648 GDScript files, 148,018 lines including comments and blank lines. Package counts include nested landmark model directories; native C++ and test lines are excluded.

Package responsibilities

data/Fetchers, parsers, contract, cache, history
generation/Pipeline, ground surface, every builder, materials
render/Camera, atmosphere, LOD, governor, presets, world cache
screens/Onboarding, map home, loading, 360 view and its tools, history, settings
map/Vector map: MVT decode, Map style, hillshade, labels
scripts/*.gdScreen manager, theme, prefs, icons, responsive rules, user-dir migration

Conventions

  • Each class opens with a ## doc comment stating its responsibility and the contract or plan task it implements.
  • Static builders with (data, ground) signatures; heavy mesh work on worker threads via MeshArrays and WorldBuildGraph.
